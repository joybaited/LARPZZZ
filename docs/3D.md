# 3d

how the phone is built, and the traps that already cost a session. read this
before touching `components/Phone.tsx`, `components/Scene.tsx` or the model
pipeline.

everything here was learned the expensive way. a rule without a reason gets
ignored at 2am, so every one of them has the reason attached.

---

## the shape of it

```
app/page.tsx
  └─ SceneMount        dynamic import, ssr: false  (keeps three out of the first bundle)
       └─ Scene        THE one <Canvas>. camera, lights, fade-in
            └─ Phone   the model: normalise -> size -> animate
```

three files, one canvas. **do not add a second `<Canvas>`.** if a design needs
3d in another section, that is a conversation about architecture, not a second
canvas — see `CLAUDE.md`.

`/tuner` is a fourth file and it is a tool, not part of the site. it is how the
phone got positioned and it is how the next adjustment should happen too.

## the model pipeline

source is 22.56MB. shipped is **3.15MB**, 2.8MB gzipped. the script that does
it is `scripts/optimize-model.mjs`.

### what was actually wrong with it

the instinct is "run draco on it." that would have done **nothing**:

| | source |
|---|---|
| geometry | already draco + meshopt, ~51k triangles, ~1.2MB |
| textures | **21.3MB of uncompressed png** |
| unused textures | 2, 1.21MB, referenced by nothing |

**measure before compressing.** the fix was never geometry. if you skip the
inspect step you will spend an afternoon tuning draco settings for a 5%
improvement on the wrong 1.2MB.

### the per-texture budget

one quality setting for every texture is the thing to avoid. the eye reads
colour maps and does not read normal maps:

| kind | resolution | quality | why |
|---|---|---|---|
| basecolour / emissive | **kept full** | webp q95 | the screen artwork is the thing people look at |
| normal / specular | halved to 1024 | webp q82 | encodes surface direction, not detail the eye resolves |

that split is where the 86% came from. the screen texture went 0.79MB -> 0.16MB
**at full resolution**, and the aluminium normal map went 10.59MB -> 0.60MB.

### the screen is texture `111`

1320x2868, bound to **both** `baseColorTexture` and `emissiveTexture`. the
emissive binding is why the screen reads as lit rather than flat grey. swapping
the image updates both, which is correct — but do not be surprised by it, and
keep the replacement at the same ratio (1:2.17).

## sizing: fractions, never constants

the rule is the same one in `LAYOUT.md`, applied to 3d: **define behaviour, not
positions.**

```tsx
const fit = viewport.height * TUNED.fit;
```

`viewport.height` is the world height visible at z=0 — a function of fov and
camera distance. a fraction of it is the same fraction of the screen on every
display, from a 390px phone to a 2560px monitor. a hard-coded `scale={2.5}` is
correct on exactly one screen.

**the mistake made here:** the first version was
`Math.min(size.width / 1400, 1) * 1.6 + 1.4` — a made-up curve fitted to pixel
width. it produced a phone at **142% of the frame** on desktop, and *bigger* on
bigger screens, which is backwards. a formula nobody can derive is a formula
nobody can fix.

## use drei. do not write bounding-box maths

```tsx
<Resize>          {/* longest axis -> 1 unit */}
  <Center>        {/* origin -> centre of the bounding box */}
    <primitive object={scene} />
  </Center>
</Resize>
```

**this replaced about forty lines of hand-rolled normalisation that was wrong
three different ways.** measure the box, divide by the longest axis, recentre,
re-measure — each attempt had its own arithmetic bug and produced a model 6 to
29 units deep, swallowing a camera sitting at z=5.

drei is already installed. it does this correctly. the forty lines were not a
clever optimisation, they were a bug surface.

### if you ever do measure a box by hand

`Box3.setFromObject()` reads **world** matrices, and on a freshly cloned gltf
they are stale. call `updateMatrixWorld(true)` first or the box is wrong and
every number derived from it is wrong.

## what this particular glb does

two things that are not obvious and will waste your time:

1. **the root node carries a baked 13x scale.** any scale you apply is
   multiplied by it. `<Resize>` neutralises this; manual maths does not, unless
   you remember.
2. **it lies flat.** screen normal is **+Y**, length is **+Z**. it has to be
   stood upright to face the camera.

the second one has a sharp edge: **if you measure the bounding box before
rotating, you get the phone's thickness as its height** — 1.53 units tall
against 4.24 wide — and every fit calculation then solves the wrong axis.
rotate first, measure second.

## the animation

the entrance is the kaktus one, 1:1 from `_ref/kaktus/docs/02` and `05`. it is a
real underdamped harmonic oscillator, not an ease curve:

```
x(t) = 1 - e^(-zeta*wn*t) * (cos(wd*t) + zeta/sqrt(1-zeta^2) * sin(wd*t))
zeta 0.65    wn 10 rad/s
```

zeta 0.65 is what produces **one or two visible overshoots** before settling.
raise it and the bounce disappears; lower it and it oscillates too long. the
overshoot is the point of the animation — scale goes 0.2 -> 1.15 -> 1, it does
not ease in.

then: idle float at 0.4Hz with a phase-shifted 1.5 degree wobble, and mouse
parallax that engages only once the entrance has settled (~1.8s).

### frame-rate independence is not optional

```tsx
easing.damp(r.rotation, "x", target, 0.35, delta);   // yes
r.rotation.x += (target - r.rotation.x) * 0.08;      // no
```

a fixed per-frame lerp moves at **different speeds on a 60Hz and a 144Hz
screen.** that is the usual reason motion "feels different on my machine."
`easing.damp` from maath takes `delta` and a smoothing time in seconds, so it is
the same everywhere. maath ships with drei — it is not a new dependency.

## the tuned values are the owner's

```
rotation [-18, 159, 6] deg    camera { z: 5.9, fov: 42 }
fit 0.72                      position centred, no offset
```

these came out of `/tuner`, chosen by eye. **do not "improve" them.** if
something looks wrong, that is a question, not an edit — `METHOD.md`.

one wrinkle worth knowing: `fit` was tuned at **0.76** with the model flat. at
the tuned angles the silhouette swings taller, so it is scaled back to 0.72 to
keep the phone off the top and bottom edges. if you change the rotation,
re-check the fit.

## verifying it, which is where the real time went

**a webgl canvas reads as empty unless you read it inside
`requestAnimationFrame`.**

the drawing buffer is cleared after each frame, so `toDataURL()` and
`readPixels()` both return 100% transparent when called normally. an hour went
into debugging an invisible model that **was rendering correctly the whole
time** — the measuring tool was broken, not the site.

```js
requestAnimationFrame(() => requestAnimationFrame(() => {
  gl.readPixels(0, 0, W, H, gl.RGBA, gl.UNSIGNED_BYTE, buf);
}));
```

or set `preserveDrawingBuffer: true` on the context, at a small performance
cost.

### the lesson under the lesson

when the probe said 0% and the code looked right, the right move was to **render
a plain red box and test the same way.** the box also read as empty — and that,
immediately, is the proof the tool is lying.

the wrong move, which is what happened instead, is to keep editing the thing
being measured. every "fix" was a guess validated by another guess. **when a
measurement disagrees with the code, suspect the measurement once before
rewriting the code three times.**

## the frameloop, and why it is not "always"

**r3f's default frameloop is `always`: it renders every frame for the life of
the page, visible or not.** the canvas is absolute inside the hero, so from
section two down it is off screen — and it was still running a full webgl
render, the entrance spring, the idle float and the parallax damping for the
whole 7492px page.

measured, draw calls per 2 seconds at 1440x900:

| scroll position | before | after |
|---|---|---|
| hero visible | 78 | 78 |
| scrolled past the hero | 78 | **0** |
| bottom of the page | **3666** | **0** |
| back at the hero | — | resumes |

the 3666 is the page bottom, where the marquee and the faq pills composite on
top of a canvas that never stopped.

`PauseOffscreen` in `Scene.tsx` is the fix: an `IntersectionObserver` on the
canvas wrapper flipping `setFrameloop` between `always` and `never`, with a
200px `rootMargin` so the phone is already moving before it is visible. this
is r3f's own documented API — no dependency.

**if you ever need the phone to animate while off screen, this is the thing in
the way.** it is deliberate.

## the environment map is self-hosted, do not go back to a preset

`<Environment preset="city" />` fetches `potsdamer_platz_1k.hdr` **from the
pmndrs github cdn on every page load**: a 301 redirect, then 1.5MB from a third
party — larger than the entire optimised model, and not covered by any cache
header we control.

measured: the hdr finished at **2284ms** while the canvas faded in at
**1242ms**, so the phone rendered for a full second with no environment
lighting and the reflections popped in afterwards. self-hosted from
`/public/hdri/`, it lands at **1305ms** and the pop is gone.

```tsx
<Environment files="potsdamer_platz_1k.hdr" path="/hdri/" />
```

same file, byte for byte — the look does not change. `files` + `path` is
drei's own supported form. **the phone's aluminium and its 0.4-roughness glass
need this map**; deleting it flattens the material, which is a design change,
not an optimisation.

## what the phone actually costs, and what it does not

worth knowing before optimising the wrong thing again — the same mistake
`optimize-model.mjs` was built to avoid:

- **geometry is not the cost.** 0.7 draw calls per frame. the scene is one
  model and a few meshes.
- **fill rate is.** `antialias: true` with `dpr={[1, 2]}` renders **5.13
  megapixels** on a retina desktop (2850x1800) against 1.28 at 1x. a 390@3x
  phone is 1.27 Mpx — the dpr cap already handles mobile; it is retina
  laptops that pay.
- the knobs, if it ever needs them, are `dpr={[1, 1.5]}` and `antialias:
  false`. **both are visible quality changes and belong to the owner**, not to
  a performance pass.

## ⚠ what has NOT been measured: the phone on a real gpu

every number above came from headless chromium on this machine, which has **no
gpu** — it falls back to swiftshader (software webgl), confirmed by
`WEBGL_debug_renderer_info` reporting `SwiftShader Device (Subzero)`. forcing
`--ignore-gpu-blocklist` did not change it.

so these two facts are solid, and they are the useful ones:

- **every non-3d part of the site runs at a locked 60fps.** `/no-hero` and
  `/pricing` both measure med 16.7ms, p95 16.7, max 16.8. the html, css, gsap
  pinning and the marquee are not the problem and do not need work.
- **100% of the measured cost is the webgl canvas.** `/` with the phone on
  screen measured med **1349.9ms** per frame against 16.7 without it.

but **1349.9ms is a software-rendering number and says nothing about a real
gpu.** a discrete or integrated gpu does this work in single-digit
milliseconds. do not quote it as the site's performance, and do not optimise
against it.

**to find out whether the hero is actually janky, open it in a real browser on
the target machine** and watch the devtools performance panel, or check
`chrome://gpu` reports hardware acceleration on. that measurement has not been
taken and cannot be taken from here.

## two css traps that look like 3d bugs

- **`-z-10` on the canvas puts it behind an opaque section background.** the
  canvas renders perfectly and you see none of it. it is `z-10` now.
- **margin collapse.** the nav's `margin-top` escaped the hero and pushed the
  whole section down, exposing the white body above it as a strip. a top margin
  on a section's first child collapses through the section — use padding on the
  section instead.

neither is a three.js problem, and both present exactly like one.

## load speed

researched and **measured** 2026-10-08. nothing in this section has been
applied yet — it is the ordered list of what to do, with the measurement that
justifies each one. the glb was opened read-only and its sha256 confirmed
identical before and after; see the three-writers warning in CLAUDE.md.

### what is actually in the file

`3.15MB` on disk. measured with `@gltf-transform`, not estimated:

| | |
|---|---|
| textures | **2.31MB — 73% of the file** |
| geometry | 51,085 triangles, 41,305 vertices |
| attributes | `POSITION`, `NORMAL`, `TEXCOORD_0` only — nothing to strip |
| already applied | `EXT_meshopt_compression` **and** `KHR_draco_mesh_compression` |

the eight textures, largest first:

| texture | px | size | bound to |
|---|---|---|---|
| `Anodized_aluminum_specularf0` | 1024² | **977KB** | `KHR_materials_specular` |
| `Anodized_aluminum_normal` | 1024² | 614KB | normal |
| `111` (the screen) | 1320x2868 | 167KB | baseColor **+ emissive** |
| `Metal_Screw_normal` | 1024² | 137KB | normal |
| `Metal_mesh_normal` | 1024² | 137KB | normal |
| `Plastic_antena_normal` | 1024² | 127KB | normal |
| `Metal_mesh_baseColor` | 1024² | 122KB | baseColor |
| `Plastic_LED_normal` | 1024² | 86KB | normal |

### ⚠ THREE THINGS THIS DOC USED TO SAY THAT ARE WRONG

1. **`specularf0` IS NOT UNUSED.** sessions 3 and 4 both listed "drop the
   unused specularf0 (0.95MB)" as the second-biggest win. it is **bound to
   `KHR_materials_specular`** on the anodized aluminium. deleting it changes
   how the body metal reads — that is a design change, not an optimisation,
   and it needs the owner and @snvzyn. *the largest remaining texture is not
   free to remove.*
2. **"2.8MB gzipped" IS NOT WHAT SHIPS.** measured: gzip -9 gives 2.90MB,
   brotli -11 gives 2.86MB. that is only **12%**, because meshopt, draco and
   webp are already compressed — there is almost nothing left for a
   general-purpose compressor to find.
3. **AND VERCEL WILL NOT COMPRESS IT AT ALL.** vercel's CDN only compresses an
   allowlist of MIME types. `model/gltf-binary` is **not on it**, and neither
   is `application/octet-stream` or `image/vnd.radiance`. so the glb and the
   hdri ship at their full byte size in production.
   **⚠ AND THE DEV SERVER HIDES THIS:** `next dev` *does* gzip the glb
   (`Content-Encoding: gzip`), so measuring locally shows a saving that
   disappears on deploy. measure compression against vercel, never localhost.

### ⚠ THE BIGGEST WIN IS NOT A FILE SIZE — IT IS A SERIAL THIRD-PARTY FETCH

measured waterfall on `/hero`, ms from navigation:

| | starts | duration | ends |
|---|---|---|---|
| `iphone.glb` (2.9MB) | 6806 | 415 | **7220** |
| `potsdamer_platz_1k.hdr` | 7130 | 190 | 7320 |
| `draco_wasm_wrapper.js` (gstatic) | 7251 | 1912 | 9163 |
| `draco_decoder.wasm` (gstatic) | 7252 | **1929** | **9181** |

`Scene.tsx` sets
`useGLTF.setDecoderPath("https://www.gstatic.com/draco/versioned/decoders/1.5.7/")`.
the decoder is only requested **after the glb has finished downloading**,
because nothing knows it is needed until the file is parsed. so there is
**~1.9s of dead time with the whole model already in memory**, waiting on
98KB from a third party.

this is the same class of bug as the `<Environment preset="city">` fetch that
session 10 removed — and the fix is the same: **self-host the decoder and hint
it early**, so it is in cache before the glb lands. it is also the cheapest
item on this list.

### in order, with the reason

1. **self-host the draco decoder** (`/public/draco/`), killing the gstatic
   hop. ~98KB, already covered by the `models|hdri|fonts` immutable header
   rule once the path is added. **removes ~1.9s of serial wait.**
2. **`<link rel="preload" as="fetch" crossorigin>` the glb and the decoder.**
   the glb is discovered only after the dynamic `Scene` chunk evaluates — a
   preload moves discovery to the HTML. ⚠ `crossorigin` is required **even
   same-origin** for `as="fetch"`, or the browser downloads it twice.
   preload sets discovery time, not priority: add `fetchpriority` to change
   the order it is fetched in.
3. **ktx2 / basis on the textures** — still the big one, and the reason is
   VRAM more than bytes:
   > webp decompresses to **full uncompressed rgba on the gpu.** a 1024²
   > texture is ~4MB of vram (plus ~33% for mipmaps) whatever the file
   > weighed. ktx2 stays compressed on the gpu — typically **4-8x less
   > vram** — and transcodes fast.

   ⚠ **the mode matters per texture, and it is not one setting:** `ETC1S` for
   colour data (`111`, `Metal_mesh_baseColor`), **`UASTC` for all six normal
   maps and the specular map.** basis's supercompression is tuned for
   correlated colour data and produces *severe artifacts* on independent
   channels like normals. this is a visual-quality decision on @snvzyn's seam
   fix, so it is theirs to approve.
   ⚠ `KTX2Loader.detectSupport(renderer)` must run before loading or the
   transcode target is wrong — the single most common ktx2 error.
4. **pre-compress the hdri, or drop it.** it gzips 1.50MB -> **1.13MB (25%)**,
   and unlike the glb it is *not* already compressed. vercel will not do it,
   so it has to ship pre-compressed, or be replaced by a smaller/baked
   environment. it is currently **48% of the model's own weight** for
   reflections on one object.
5. **`renderer.compileAsync(scene, camera)`** while the preloader is still up,
   so shader compilation does not land as a hitch on first paint.

### what is already done, do not redo it

- `useGLTF.preload(MODEL)` at module scope in `Phone.tsx` — the drei-level
  preload is in place. it starts the fetch when the chunk evaluates, which is
  why item 2 above is about the *HTML*, not about drei.
- `dynamic(() => import("./Scene"), { ssr: false })` — three.js is out of the
  initial bundle.
- `<Suspense>` + `useProgress`, and the canvas fades in when the pipeline is
  ready.
- immutable cache headers on `models|hdri|fonts` (`next.config.ts`).
- the hdri is self-hosted — no third-party CDN for it any more.
- `IntersectionObserver` pausing the frameloop off-screen (`PauseOffscreen`).
- geometry is meshopt + draco and carries no unused attributes. **there is no
  geometry win left here** — 51k triangles is small, and the file is 73%
  texture.

### the honest ceiling

kaktus is fast partly because spline streams a purpose-built format and partly
because it sits on a cdn. with ktx2, a self-hosted decoder and a preload we are
in the same league. the rest is hosting, not code.

⚠ **and none of it should be tuned against this machine's numbers.** headless
chromium here has no gpu (`SwiftShader`), so frame timings are ~100x off. the
waterfall above is a *network* measurement, which is valid; any frame-time
claim needs real hardware and `chrome://gpu`.
